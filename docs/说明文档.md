## 1. 项目全景

一个**差速轮式移动机器人**在 Gazebo 里的完整导航仿真，技术栈：

```
URDF/xacro 机器人模型
   │  xacro 展开
   ▼
robot_state_publisher ──► 静态 TF（base_link → 各 link）
   │
   ▼  spawn 进 Gazebo
Gazebo 插件 ──► /demo/odom（轮式里程计）、/livox/imu、/livox/lidar（点云）
   │
   ▼
FAST-LIO ──► /Odometry + odom → base_link TF（LiDAR + IMU 紧耦合）
   │
   ▼
Nav2 ──► map_server(静态地图) + AMCL(定位) + planner(全局规划) + controller(局部跟踪) + BT(编排)
   │
   ▼
/cmd_vel ──► Gazebo diff_drive 驱动轮子
```

本项目是标准 colcon 工作区，含**三个包**：`sam_bot_description`（机器人描述 + 导航配置）、`mid360_simulation`（Mid-360 仿真插件）和 `fast_lio`（LiDAR+IMU 紧耦合里程计 FAST-LIO，替代原 robot_localization EKF）。导航栈使用 Nav2 官方插件，里程计由 FAST-LIO 提供：

| 环节 | 插件 |
|------|------|
| 全局规划 | `nav2_navfn_planner/NavfnPlanner`（NavFn / Dijkstra） |
| 局部控制 | `nav2_mppi_controller::MPPIController`（MPPI 采样） |
| 定位 | `nav2_amcl::DifferentialMotionModel`（AMCL，发布 map→odom） |
| 里程计 | FAST-LIO（`fast_lio`，LiDAR+IMU 紧耦合，发布 odom→base_link） |
| 恢复行为 | `nav2_behaviors`（Spin / BackUp / DriveOnHeading / Wait / AssistedTeleop） |
| 建图（离线） | `slam_toolbox`（`online_async`，发布 map→odom + `/map`） |

> **建图是另一条链路**：`build_map.sh` 启动 `display.launch.py`（Gazebo + FAST-LIO + 点云转激光）再起 `slam_toolbox online_async`，键盘遥控边开边建，结束时用 `nav2_map_server/map_saver_cli` 把 `/map` 存成 `map/my_map.yaml` + `.pgm`。建完图后的导航仍然用这份静态地图 + AMCL 定位，**运行期不再有任何 slam 节点**。详见 §4.3 与 [运行文档 §3.3](运行文档.md)。

## 3. 硬件环境

### 3.1 机器人硬件平台（被仿真对象）

机器人 `sam_bot` 是一个 **0.42 × 0.31 × 0.18 m、约 16.8 kg** 的差速轮式移动小车，硬件全部由 `src/sam_bot_description/description/sam_bot_description.urdf` 定义（xacro 展开）。Gazebo 里的每个 `<gazebo>` 段就是一个"虚拟硬件"及其驱动插件。

#### 3.1.1 车体与整体参数

| 项 | 值 | 说明 |
|----|-----|------|
| 车体尺寸（长×宽×高） | 0.42 × 0.31 × 0.18 m | `base_link` 箱体，青色 |
| 车体质量 | 15 kg | 含箱体惯量（`box_inertia`） |
| 整机质量 | ≈16.8 kg | 车体 + 2 轮(0.5×2) + 万向球(0.5) + IMU(0.1) + 激光(0.125) + 相机(0.035) |
| 导航基准点 | `base_footprint` | 车体正下方 0.15 m（`wheel_radius + wheel_zoff`），2D 代价地图用它定位 |

#### 3.1.2 驱动系统（差速驱动）

| 项 | 值 | 说明 |
|----|-----|------|
| 驱动方式 | 差速（differential drive） | 两独立驱动轮 + 一个自由万向球 |
| 轮子半径 / 直径 | 0.10 m / 0.20 m | 每轮宽 0.04 m、0.5 kg，**continuous** 关节（绕 y 轴） |
| 轮距（wheel_separation） | 0.36 m | 两轮中心横向间距 |
| 轮子安装位置 | x=−0.12 m，y=±0.18 m | 车体后部两侧（`x_reflect=-1`） |
| 最大轮扭矩 | 20 N·m | `max_wheel_torque` |
| 最大轮角加速度 | 3.0 rad/s² | `max_wheel_acceleration` |
| 前进速度上限 | 0.5 m/s（后退 −0.35 m/s） | 由 Nav2 MPPI `vx_max/vx_min` 约束 |
| 角速度上限 | 1.9 rad/s | Nav2 MPPI `wz_max` |

执行器插件 `libgazebo_ros_diff_drive.so`：订阅 `/cmd_vel`（Twist），把 `vx/wz` 换算成左右轮转速；发布 `/demo/odom`，并且 **`publish_odom_tf=false`**（odom→base_link 的 TF 交给 FAST-LIO 发，避免重复发布同一 TF）。`/demo/odom` 只保留给 Nav2 controller/velocity_smoother 读速度反馈。

#### 3.1.3 传感器

| 传感器 | link / frame | 话题 | 频率 | 关键参数 |
|--------|-------------|------|------|----------|
| IMU | `livox_imu` | `/livox/imu` | 200 Hz | 内置于 Mid-360（BMI088）：角速度 stddev 1e-5、线加速度 stddev 1e-4；装在雷达内 (0.011, 0.02329, −0.04412) |
| 激光雷达 | `livox` | `/livox/lidar`（PointCloud2） | 10 Hz | 非重复扫描 3D 点云、量程 0.1~15.0 m、测距噪声 stddev 0.01 m；装在车体上方 0.12 m |
| 2D 激光（投影） | `base_link` | `/scan`（LaserScan） | 10 Hz | 由 `pointcloud_to_laserscan` 把 `/livox/lidar` 投影得到，供 AMCL/代价地图使用 |
| 深度相机 | `camera_depth_frame` | `/depth_camera/*` | 30 Hz | 640×480、水平 FOV 60°（1.047 rad）、量程 0.05~3 m、双目基线 0.2 m；装在前上方 (0.215, 0, 0.05) m |

> `/scan` 15.0 m 的量程（由 `/livox/lidar` 投影）直接决定了 AMCL 的观测距离和代价地图的障碍感知范围；FAST-LIO 用 LiDAR+IMU 紧耦合输出 odom→base_link，替代 EKF 修正纯轮式里程计的航向漂移。
>
> **Mid-360 仿真注意点**（`mid360.xacro`）：射线传感器必须带 `<always_on>true</always_on>` 才会持续发点云（缺失时 `/livox/lidar` 几乎静默）；`point_rate=200000` + `downsample=20` 保证每帧覆盖 360° 全向（约 1000 条射线/帧），否则 FAST-LIO 报 "Too few input point cloud!"。

### 3.2 仿真主机环境（运行 Gazebo/ROS2 的机器）

| 项 | 值 |
|----|-----|
| 操作系统 | Ubuntu 22.04 LTS（内核 6.8.0） |
| ROS 2 | Humble Hawksbill（`/opt/ros/humble`） |
| 仿真器 | Gazebo Classic（`gazebo_ros`） |
| CPU | Intel Core i7-14650HX |
| 内存 | 8 GB（仿真时 gzserver 常驻较高 CPU） |
| GPU | **VMware SVGA II（虚拟显卡）** |
| 磁盘 | 98 GB（可用约 61 GB） |

> **本机是 VMware 虚拟机，虚拟显卡是 rviz2 GL 问题的根源**：SVGA II 的 OGRE/Mesa 实现不支持 GL3+ core profile 下 Nav2 代价地图着色器所用的 `sampler1D`（1D 纹理），所以启动时强制 `MESA_GL_VERSION_OVERRIDE=2.1` 退回旧版 RenderSystem；同时 Qt GTK 主题需要 `GSETTINGS_SCHEMA_DIR` 与 `QT_QPA_PLATFORM=xcb`。详见 [运行文档 §6.4](运行文档.md)。

## 4. 仿真世界与地图

### 4.1 世界（`src/sam_bot_description/world/my_world.sdf`）

约 10×10 m 的封闭场地，四面墙（北/南在 y=±5，东/西在 x=±5，墙厚 0.2 m、高 1 m），内部两个障碍物：

| 障碍物 | 位置 (x, y) | 尺寸 |
|--------|-------------|------|
| `unit_box`（正方体） | (1.513, −0.181) | 1×1×1 m |
| `unit_sphere`（球体） | (−1.895, 2.368) | 半径 0.5 m |

地面摩擦 μ=1.0，重力 −9.8，物理引擎 ODE。

### 4.2 地图（`src/sam_bot_description/map/my_map.yaml` + `my_map.pgm`）

| 项 | 值 | 含义 |
|----|-----|------|
| `image` | `my_map.pgm` | 占用栅格图像（**必须是同目录下真实存在的文件名**） |
| `resolution` | 0.05 | 每像素 5 cm |
| `origin` | `[-4.98, -4.99, 0]` | 地图左下角在 map 坐标的位置（随每次建图略有变化） |
| `mode` | `trinary` | 三值（占用/自由/未知） |
| `occupied_thresh` / `free_thresh` | 0.65 / 0.25 | 占用/自由判定阈值 |

地图约 **198×199 像素**，覆盖约 `[-4.98, 4.92] × [-4.99, 4.96]`（map 坐标），与四面墙围成的区域对齐。`map` 坐标 (0,0) 即场地中心。`origin` 和尺寸由 `map_saver_cli` 按本次建图的实际范围自动写入，重新建图后会变。

### 4.3 建图流程（`build_map.sh` + `slam_toolbox`）

导航用的是**离线建好的静态地图**。需要重新建图时走另一条链路，与导航链路互斥：

```
Gazebo（/livox/lidar 点云 + /livox/imu）
   │
   ├──► FAST-LIO ──► odom → base_link TF
   │
   └──► pointcloud_to_laserscan ──► /scan（2D）
                                        │
                                        ▼
                            slam_toolbox online_async
                            ├── 栅格建图（CSM 扫描匹配 + 回环）
                            ├── 发布 /map
                            └── 发布 map → odom TF
                                        │
键盘遥控 /cmd_vel ───────────────────────┘
按 Ctrl+C ──► map_saver_cli ──► map/my_map.yaml + my_map.pgm
```

关键参数（`config/mapper_params_online_async.yaml`）：

| 参数 | 值 | 说明 |
|------|-----|------|
| `odom_frame` / `map_frame` / `base_frame` | `odom` / `map` / `base_footprint` | 与本项目 TF 树一致 |
| `scan_topic` | `/scan` | 由 Mid-360 点云投影得到 |
| `max_laser_range` | 15.0 | 与 Mid-360 量程一致（官方默认 20.0） |
| `transform_timeout` | **1.0** | 见下方说明；官方默认 0.2 不够 |
| `scan_queue_size` | **30** | 扫描消息队列深度，防止等 TF 时溢出丢帧 |

> **为什么 `transform_timeout` 要放大到 1.0**：FAST-LIO 发布 `odom→base_link` 比 `/scan` 晚约 0.2 s（要先处理完点云）。`slam_toolbox` 的 `tf2_ros::MessageFilter` 拿到一帧扫描后，会在**该扫描的时间戳**上查 TF，查不到就排队等；默认 `transform_timeout: 0.2` + 很小的队列，会持续打印
> `Message Filter dropping message: frame 'base_link' ... queue is full` 并丢掉绝大多数扫描——表现是**地图几乎不更新**（车开了几米地图只多几格）。

## 5. Nav2 配置详解

文件：`src/sam_bot_description/config/nav2_params.yaml`，共 **15 个 `ros__parameters` 段**，每段都带 `use_sim_time: True`（**必须**，见 [运行文档 §6.3](运行文档.md)）。

### 5.1 插件命名规则（`::` vs `/`）

Nav2 加载插件时，`plugin:` 字段的查找键取决于**插件 XML 是否带 `name` 属性**：

| 插件 | `plugin:` 该写 | 依据 |
|------|---------------|------|
| `nav2_navfn_planner/NavfnPlanner` | 斜杠 | 官方 XML 有 `name` |
| `nav2_behaviors/Spin`（BackUp/DriveOnHeading/Wait/AssistedTeleop 同） | 斜杠 | 官方 XML 有 `name` |
| `nav2_mppi_controller::MPPIController` | 双冒号 | 官方 XML 只有 `type` |
| `nav2_controller::SimpleGoalChecker` / `SimpleProgressChecker` | 双冒号 | 同上 |
| `nav2_costmap_2d::ObstacleLayer` 等代价图层 | 双冒号 | 同上 |
| `nav2_smoother::SimpleSmoother` | 双冒号 | 同上 |
| `nav2_waypoint_follower::WaitAtWaypoint` | 双冒号 | 同上 |

规则：**看插件 XML 里有没有 `<class name="...">`**——有 `name` 就用 `name`（斜杠），只有 `type` 就用 `type`（双冒号）。写错报 `class ... does not exist. Declared types are ...`。

### 5.2 amcl（定位）

| 参数 | 值 | 含义 |
|------|-----|------|
| `base_frame_id` | `base_footprint` | 机器人参考帧 |
| `global_frame_id` / `odom_frame_id` | `map` / `odom` | 发布 map→odom TF |
| `laser_model_type` | `likelihood_field` | 似然场模型 |
| `laser_max_range` | `15.0` | 观测量程（须 ≥ 世界墙距 ~5 m；曾误设 4.0 导致 4.9 m 的墙被截断、AMCL 无法匹配） |
| `min/max_particles` | 500 / 2000 | 粒子数范围 |
| `robot_model_type` | `nav2_amcl::DifferentialMotionModel` | 差速运动模型 |
| `scan_topic` | `scan` | 激光话题 |
| `update_min_d` / `update_min_a` | 0.25 m / 0.2 rad | 移动多远/转多少才更新一次 |
| `transform_tolerance` | 1.0 | TF 容差 |

### 5.3 controller_server（局部控制，MPPI）

```yaml
controller_frequency: 20.0
controller_plugins: ["FollowPath"]
FollowPath:
  plugin: "nav2_mppi_controller::MPPIController"
  time_steps: 56;  model_dt: 0.05    # 2.8 s 前瞻
  batch_size: 2000                   # 采样轨迹条数
  vx_max: 0.5;  vx_min: -0.35        # 线速度范围（负值允许后退）
  wz_max: 1.9                        # 角速度上限
  motion_model: "DiffDrive"
  temperature: 0.3;  gamma: 0.015
  critics: [ConstraintCritic, CostCritic, GoalCritic, GoalAngleCritic,
            PathAlignCritic, PathFollowCritic, PathAngleCritic, PreferForwardCritic]
```

- `CostCritic` 用足迹做碰撞检测（`consider_footprint: true`、`critical_cost: 300`）；
- `GoalAngleCritic` + `PreferForwardCritic` 保证到点后摆正朝向；
- 目标检查器 `general_goal_checker`：`xy_goal_tolerance: 0.25`、`yaw_goal_tolerance: 0.25`、`stateful: True`。

### 5.4 planner_server（全局规划，NavFn）

```yaml
planner_plugins: ["GridBased"]
GridBased:
  plugin: "nav2_navfn_planner/NavfnPlanner"
  tolerance: 0.5
  use_astar: false      # Dijkstra
  allow_unknown: true
```

### 5.5 两个代价地图

| | global_costmap | local_costmap |
|--|----------------|---------------|
| 坐标系 | `map` | `odom`（滚动窗口） |
| 尺寸 | 整图 | 3×3 m 窗口，分辨率 0.05 |
| 图层 | static + obstacle + inflation | voxel + inflation |
| 障碍观测 | `/scan` | `/scan` |
| 膨胀 | `inflation_radius: 0.55`、`cost_scaling_factor: 3.0` | 同左 |
| 足迹 | `robot_radius: 0.3` | `[[0.21,0.195],[0.21,-0.195],[-0.21,-0.195],[-0.21,0.195]]` |

### 5.6 behavior_server（恢复行为）

```yaml
behavior_plugins: ["spin", "backup", "drive_on_heading", "assisted_teleop", "wait"]
```

`spin` 原地旋转、`backup` 后退、`wait` 等待等，供行为树在卡住时触发恢复。注意：默认行为树里的 `BackUp` 节点依赖这里的 `backup` action server（若移除 `backup` 需改用 `src/sam_bot_description/behavior_trees/*no_backup.xml`）。

### 5.7 velocity_smoother（速度平滑）

`controller_server` 发布 `/cmd_vel_nav` → `velocity_smoother` 限幅平滑后发 `/cmd_vel` → Gazebo。参数：`max_velocity [0.5, 0, 2.0]`、`min_velocity [-0.5, 0, -2.0]`、`max_accel [2.5, 0, 3.2]` 等。

### 5.8 其余段

| 段 | 说明 |
|----|------|
| `bt_navigator` | 编排导航（`NavigateToPoseNavigator` / `NavigateThroughPosesNavigator`），`odom_topic: /demo/odom` |
| `map_server` | 加载静态地图（`yaml_filename` 启动时被 bringup 的 `map` 参数改写） |
| `map_saver` | 保存地图 |
| `smoother_server` | `SimpleSmoother`，平滑全局路径 |
| `waypoint_follower` | 多航点任务（`WaitAtWaypoint`，每点停 200 s） |
| `collision_monitor` / `docking_server` / `loopback_simulator` | 参数文件里有配置段，但**默认 bringup 不加载** |

## 6. 坐标关系与数据流

### 6.1 TF 树

```
map ──► odom ──► base_link ──► base_footprint
                     ├──► drivewhl_l/r_link
                     ├──► front_caster
                     ├──► livox_imu
                     ├──► livox
                     └──► camera_link ──► camera_depth_frame
```

| TF | 发布者（导航时） | 发布者（建图时） |
|----|------------------|------------------|
| `map → odom` | AMCL（激光与地图匹配） | slam_toolbox（扫描匹配） |
| `odom → base_link` | FAST-LIO（`/livox/lidar` + `/livox/imu` 紧耦合） | FAST-LIO |
| `base_link → 各 link` | robot_state_publisher（URDF） | robot_state_publisher |

> `map→odom` 的发布者**同时只能有一个**。导航时必须确保没有残留的 `slam_toolbox` 在跑，否则它会和 AMCL 抢同一个 TF（见 [运行文档 §6.9](运行文档.md)）。

### 6.2 速度控制链

```
controller_server ──/cmd_vel_nav──► velocity_smoother ──/cmd_vel──► diff_drive
behavior_server(恢复) ─────────────────────/cmd_vel──► diff_drive
```

### 6.3 一次导航数据流

```
RViz 2D Nav Goal ──► bt_navigator ──► planner_server ──► 全局路径
                                                              │
                                          controller_server(MPPI) ◄── local_costmap
                                                              │
                              /cmd_vel_nav ──► velocity_smoother ──► /cmd_vel ──► diff_drive
                                                              │
                              轮子转 ──► /livox/lidar + /livox/imu ──► FAST-LIO ──► /Odometry + odom→base_link
                              /scan ──► AMCL ──► map→odom；代价地图更新 ──► 直到到达
```

更完整的话题速查表与数据流图见 [architecture.md §9](architecture.md)。
