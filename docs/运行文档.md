## 3. 启动项目

### 3.1 完整导航仿真（推荐）

一次启动 **Gazebo（世界+机器人）+ FAST-LIO + 完整 Nav2 导航栈 + RViz**：

```bash
cd /home/lunyi/myrosproject/CleanRobot_ws
source /opt/ros/humble/setup.bash
source install/setup.bash

# ↓ 本机（Ubuntu 22.04 + 该 Qt/GL 环境）需要的两个环境变量，见 6.4 节
export GSETTINGS_SCHEMA_DIR=$HOME/.local/share/glib-2.0/schemas
export QT_QPA_PLATFORM=xcb

ros2 launch sam_bot_description navigation.launch.py
```

`navigation.launch.py` 依次拉起：

```
gzserver（加载 src/sam_bot_description/world/my_world.sdf）
gzclient（Gazebo 图形界面）
robot_state_publisher（xacro 展开 URDF → 发布 base_link→* 的静态 TF）
spawn_entity（把机器人 spawn 进 Gazebo）
fastlio_mapping（FAST-LIO，LiDAR+IMU 紧耦合 → 发布 /Odometry 和 odom→base_link TF）
nav2_bringup / navigation_launch.py（planner / controller / BT / smoother ...）
map_server + lifecycle_manager_localization（加载 2D 静态地图，供代价地图使用）
fastlio_relocalization（3D 点云重定位：先验 PCD 全局搜索 + ICP → 发布 map→odom TF）
rviz2（加载 Nav2 官方默认视图 nav2_default_view.rviz）
```

> ⚠️ **这里没有任何建图节点**：`map_server` 只负责加载 2D 静态地图，`fastlio_relocalization` 负责 3D 定位（已完全取代 AMCL）。若 RViz 里看到地图"边走边长"，说明有残留的 `slam_toolbox` 在跑（见 6.9）。需要重新建 2D 地图请用 §3.3 的 `./build_map.sh`；需要重新生成 3D 先验点云请用 §3.4 的 `./build_3d_map.sh`。
>
> ⚠️ **不再需要人工给初始位姿**：启动后 `fastlio_relocalization` 会自动在先验 PCD 上做 (x, y, yaw) 全局搜索 + ICP，2~3 秒内自己找到位置，日志里出现 `全局重定位成功` 即可。AMCL 的 "2D Pose Estimate" 操作已不再需要。

### 3.2 只显示模型与仿真（无导航）

启动 **Gazebo + 机器人 + FAST-LIO + RViz**，但不启动 Nav2 导航栈，可用于检查模型/传感器/仿真本身：

```bash
cd /home/lunyi/myrosproject/CleanRobot_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
export GSETTINGS_SCHEMA_DIR=$HOME/.local/share/glib-2.0/schemas
export QT_QPA_PLATFORM=xcb

ros2 launch sam_bot_description display.launch.py
# 参数： gui:=False（启用命令行版 joint_state_publisher，而非 GUI 版）
```

`display.launch.py` 用 `gazebo --verbose`（GUI+server 合体）、`robot_state_publisher`、`spawn_entity`、`fastlio_mapping`、`pointcloud_to_laserscan` 和加载 `urdf_config.rviz` 的 `rviz2`，不含 Nav2。

### 3.3 一键键盘建图（重新生成地图）

导航用的是**已建好的静态地图**；只有在场地变化、需要重新建图时才跑这一条。脚本会自己清理残留进程、起仿真和 slam、等 `/scan` 和 `/map` 就绪，然后把键盘交给你。

```bash
cd /home/lunyi/myrosproject/CleanRobot_ws
./build_map.sh            # 默认存成 map/my_map（会覆盖原图）
./build_map.sh my_map2    # 指定地图名
```

脚本做的事：

1. 清理残留的 gzserver / FAST-LIO / slam_toolbox / teleop 等进程；
2. 后台起 `display.launch.py gui:=False`（Gazebo + FAST-LIO + 点云转 `/scan` + RViz）；
3. 等 `/scan` 有数据后，后台起 `slam_toolbox online_async_launch.py`（用 `config/mapper_params_online_async.yaml`），并等 `/map` 首次出现；
4. 前台跑 `teleop_twist_keyboard`，你边开边建（RViz 里能实时看到地图长大）；
5. 按 **Ctrl+C** 结束驾驶 → 自动 `map_saver_cli` 保存地图 → 清理后台进程。

保存逻辑的几点保证：

- **不依赖 trap**：`teleop` 退出后主流程会直接保存，Ctrl+C 的 trap 只是快速路径；
- **每 20 秒后台自动落盘一次**，即使脚本被强杀最多丢 20 秒成果；
- 保存前先停掉自动保存，避免两个 `map_saver` 同时写同一个文件；
- 保存后校验 `.yaml` / `.pgm` 是否真的存在，失败会提示去看 `/tmp/build_map_slam.log`。

```
src/sam_bot_description/map/<地图名>.yaml + .pgm
```

> 建完图**不要马上跑导航**：先确认 `/map` 已保存（文件存在且大小合理），再 `./run.sh`。`run.sh` 现在会把残留的 `slam_toolbox` 一并清掉，避免两边同时抢 `map→odom`。

### 3.4 一键生成 3D 先验点云（重定位用）

`fastlio_relocalization` 需要一个 **3D PCD 先验地图**做 ICP 配准。默认文件是 `src/sam_bot_description/map/prior_3d_map.pcd`（已随仓库提供）。只有在**世界/障碍物改了**、或想换一套更干净的点云时才需要重新生成：

```bash
cd /home/lunyi/myrosproject/CleanRobot_ws
./build_3d_map.sh                     # 默认写 src/sam_bot_description/map/prior_3d_map.pcd
./build_3d_map.sh /tmp/other_map.pcd  # 写到别处
```

脚本做的事：

1. 清理残留进程，用 `display.launch.py gui:=False rviz:=False` 起 Gazebo + FAST-LIO；
2. 用 **mapping 专用配置** `src/fast_lio/config/mid360_sim_mapping.yaml`
   （`point_filter_num: 1`、更细的体素、`publish.map_en: true`、`pcd_save_en: true`）；
3. 等 `/Odometry` 有 10 Hz 输出后，跑 `tools/auto_drive_map.py` 自动绕一圈采集点云；
4. 调 `ros2 service call /map_save std_srvs/srv/Trigger`，FAST-LIO 把它内部累积的
   `pcl_wait_pub`（odom 系）写成二进制 PCD；
5. 用 `fastlio_localization/tools/shift_pcd.py` 把 PCD 的 x/y 平移 IMU 安装偏移
   `(0.3335, 0.0233)` m——FAST-LIO 的原点是建图起点的 **IMU**，而 2D 栅格图的原点是
   建图起点的 **base_link**；不平移两者会差 0.33 m（详见 §6.6「RViz 没撞、Gazebo 撞」）；
6. 在 `install/.../share/sam_bot_description/map/` 里补一条指向新 PCD 的软链
   （`--symlink-install` 只在 build 时给已存在的文件建链），然后关闭仿真。

> **先验地图的坐标系**：PCD 经第 5 步后与 2D 地图同为“建图起点 `base_link`”坐标系；
> 导航时 `fastlio_relocalization` 直接对这个 PCD 做配准，求出的变换就是 `map→odom`。
> 因此 2D 地图（`my_map`）和 3D 点云必须在**同一次场地**里生成；改了世界文件就要两份
> 地图一起重建。z 不平移：保持雷达平面为 0，与重定位的 `constrain_planar` 一致。

> **PCD 已入库**：`.gitignore` 里 `*.pcd` 是排除规则，但对
> `src/sam_bot_description/map/prior_3d_map.pcd` 做了显式例外，新克隆的工作区
> `colcon build --symlink-install` 后就能直接导航，不必先生成地图。

## 4. 运行后的操作流程

启动完成后，导航栈会自动配置并激活。**没有初始位姿需要人工设置**——3D 重定位节点会自己找位置。

### 4.1 等待 3D 全局重定位完成（自动）

`fastlio_relocalization` 启动后先发单位阵 `map→odom` 让 TF 链连通，然后等第一帧
`/cloud_registered`，在 0.5 m / 15° 的 (x, y, yaw) 栅格上做全局搜索，再用 ICP 精配准。
默认 spawn 在原点时，终端里 2~3 秒内会出现：

```
[fastlio_relocalization]: 全局搜索使用上部结构：z >= -0.36 m，912 点（全图 6307 点）
[fastlio_relocalization]: 开始全局重定位：在 0.50 m 栅格上搜索 (x, y, yaw) ...
[fastlio_relocalization]: 全局重定位成功：内点率 1.00，平均最近邻距离 0.066 m，
                          map->odom = (x=0.10, y=-0.04, yaw=0.4°)，耗时 0.55 s
```

看到 `全局重定位成功` 即完成。之后每帧点云都会用 ICP 跟踪，10 Hz 发布 `map→odom`。

> **不需要 RViz 的 "2D Pose Estimate"**：AMCL 已经移除。`2D Pose Estimate` 按钮即使点了
> 也不会有人订阅；要强制重新定位，调用下面的服务：
>
> ```bash
> ros2 service call /relocalize std_srvs/srv/Trigger "{}"
> ```
>
> 机器人被搬动/传送后、或日志出现 `3D 跟踪失败` 连续 5 次时，节点也会自动重新全局搜索。
>
> **歧义提示**：若日志出现 `全局重定位存在歧义：最优 ... 得分 ...，次优 ...`，说明场地
> 存在对称解（正方形围墙的 90° 旋转、或者先验地图里有抖动鬼影）。节点仍会选得分最高
> 的解，但会打印告警；如果 RViz 里点云明显没对齐，请检查先验地图或重新执行 §3.4。
> 站在正方形场地中心附近时这条告警几乎必然出现（四个角互为对称），只要最优解与真值
> 一致、点云重合，可以忽略。

### 4.2 下发目标点

1. 工具栏点 **2D Nav Goal**（紫色箭头图标）；
2. 在地图上点目标位置并拖出期望朝向。

机器人随即开始：全局规划（NavFn）→ 局部跟踪（MPPI）→ 到达后原地摆正到目标朝向 → `Goal succeeded`。

### 4.3 判断是否成功

- 终端出现 `[controller_server] Reached the goal!` 和 `[bt_navigator] Goal succeeded`。
- 机器人停在目标点（误差 < `xy_goal_tolerance`，默认 0.25 m）并把朝向摆到目标朝向（误差 < `yaw_goal_tolerance`，默认 0.25 rad）。

## 5. 验证与调试命令

```bash
# 已启动的节点
ros2 node list

# TF 树是否完整（map→odom→base_link→livox 等）
ros2 run tf2_ros tf2_echo map base_link
ros2 run tf2_ros tf2_echo odom base_link

# 话题是否在发
ros2 topic list
ros2 topic echo /scan --once          # 2D 激光（由 /livox/lidar 投影得到）
ros2 topic echo /livox/lidar --once   # Mid-360 3D 点云
ros2 topic echo /demo/odom --once     # 里程计
ros2 topic echo /livox/imu --once     # Mid-360 内置 IMU
ros2 topic hz /livox/lidar             # 点云频率（应约 10 Hz）
ros2 topic hz /scan                    # 激光频率（应约 10 Hz）

# FAST-LIO 里程计（odom→base_link）
ros2 topic echo /Odometry --once

# 3D 重定位结果（map 系 base_link 位姿，10 Hz）
ros2 topic echo /localization_pose --once
ros2 topic hz /localization_pose

# 强制重新全局重定位（搬动机器人后）
ros2 service call /relocalize std_srvs/srv/Trigger "{}"

# 先验点云 / 当前帧配准后的点云（RViz 里可加 PointCloud2 显示）
ros2 topic echo /prior_map --once --field width   # transient_local，晚加入也能收到
ros2 topic hz /aligned_scan                       # 配准后的当前帧，约 10 Hz

# 地图是否在发布（导航时应由 map_server 发布，不是 slam_toolbox）
ros2 topic info -v /map
ros2 topic echo /map --once --field info.width
ros2 lifecycle get /map_server        # 应为 active [3]

# 各 action server 是否就绪
ros2 action list

# 手动下发一个目标（不依赖 RViz）
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: 2.0, y: 2.0, z: 0.0}, orientation: {w: 1.0}}}}"

# 查看节点参数（例如确认 use_sim_time）
ros2 param get /fastlio_relocalization use_sim_time
ros2 param get /fastlio_relocalization global_search_height
```

### 5.1 点云密度与定位漂移快速自检

导航过程中若怀疑「车飘 / 定位跳」，用下面几条命令把**点云密度**和**重定位是否漂**量化出来，不要凭 RViz 观感猜：

```bash
# ① 每帧点数（当前 downsample=8 的健康值约 590 点/帧，范围 585~595）
ros2 topic echo /livox/lidar --once --field width
#   只有 ~200 点 → 检查 mid360.xacro 的 <downsample> 是否被改大
#   直接崩溃 → downsample 太小（见 6.12）

# ② Gazebo 真值：输出 "x y z roll pitch yaw"（物理车体 base_link 在世界系）
gz model -m sam_bot -p

# ③ 3D 重定位估计位姿（map 系，物理 base_link 位姿，可直接和 ② 对比）
ros2 topic echo /localization_pose --once --field pose.pose.position

# ④ map→odom 校正量：正常应平滑、小幅变化；
#    若在几米范围内反复跳变，说明 ICP 跟丢（见 6.6）
ros2 run tf2_ros tf2_echo map odom
```

判读标准（实测参考）：

- **静止**时 `/localization_pose` 与 Gazebo 真值的差在原点附近约 **2~5 cm**；跑过几米后
  受先验地图自身漂移影响，可能到 **10~20 cm**，属正常范围。
- **运动中**由于 `/localization_pose` 用 `now()` 打时间戳、而 FAST-LIO 的点云/位姿本身有约
  0.1~0.2 s 延迟，直接比对会出现 0.1~0.2 m 的“假误差”；要看趋势，不要看单帧。
- `map→odom` 不应出现米级跳变。`/aligned_scan` 在 RViz 里应与 `/prior_map` 的墙线/箱体
  重合；明显错位时看 6.6。
- **坐标系已对齐**：FAST-LIO 发布 `odom→base_link` 时会补偿 IMU 安装偏移
  （`body_to_base_T`），`build_3d_map.sh` 保存 PCD 后也会把 x/y 平移到建图起点的
  `base_link`。所以 `/localization_pose`、`map→base_link` 都可以**直接**和 `gz model`
  真值比较，不需要再换算 0.35 m 的 IMU 偏移。

### 5.2 TF 树与导航栈全链路自检

启动完成后，用下面几条把「TF 树是否闭合、生命周期是否就绪、代价地图是否收到激光、定位是否对准真值」一次性确认：

```bash
# ① TF 树是否闭合（应看到 map→odom→base_link→base_footprint，以及
```

## 6. 常见问题排查

### 6.1 导航栈起不来 / 报 `class ... does not exist`

```
Failed to create global planner. Exception: ... class nav2_navfn_planner::NavfnPlanner
with base class type nav2_core::GlobalPlanner does not exist. Declared types are nav2_navfn_planner/NavfnPlanner ...
```

原因：`nav2_params.yaml` 里 `plugin:` 字段写错了。**Nav2 插件的查找键**分两种（详见 [说明文档.md §5.2](说明文档.md)）：

- 插件 XML **带 `name` 属性**的 → 用 `name`（斜杠），例如 `nav2_navfn_planner/NavfnPlanner`、`nav2_behaviors/Spin`；
- 插件 XML **只有 `type`** 的 → 用 C++ 类名（双冒号），例如 `nav2_mppi_controller::MPPIController`、`nav2_controller::SimpleGoalChecker`、代价地图各层。

### 6.2 `parameter 'yaml_filename' is not initialized`（map_server 起不来）

`nav2_params.yaml` 里 `map_server.ros__parameters.yaml_filename` 被注释掉了。启动时 Nav2 的 `RewrittenYaml` 只**改写已存在的键**，不会凭空注入，所以这个键必须存在（哪怕是空字符串 `""`）。

### 6.3 下发目标后机器人不动 / 瞬间 `Reached the goal!` / `Transform data too old`

根因通常是 **`use_sim_time` 缺失**：`nav2_params.yaml` 的每个 `ros__parameters` 段都必须有 `use_sim_time`（本文件共 15 处）。一旦缺失，Nav2 节点用墙钟时间、Gazebo 用 `/clock` 仿真时间，两者对不上，表现为：

- `Transform data too old when converting from map to odom`；
- 目标刚下发就 `Reached the goal!`，但车根本没动。

确认方法：`grep -c use_sim_time src/sam_bot_description/config/nav2_params.yaml` 应等于 15。

> 另一个易混淆的瞬时现象：**启动初期** FAST-LIO 要收到首帧 lidar+IMU 才开算、且 gzserver 加载世界时吃满 CPU，会出现短暂的 `Timed out waiting for transform`、`Failed to meet update rate` 和 TF `unconnected trees`，这些会随 FAST-LIO 输出 `odom→base_link` 后自动消失，不是故障。

### 6.4 rviz2 / joint_state_publisher_gui 启动即崩溃（本机专属）

本机（Ubuntu 22.04 + gnome-settings-daemon 42 + Qt GTK 主题）上，rviz2 会因 `GLib-GIO-ERROR: ... 'antialiasing'` 崩溃。**启动前必须 export**：

```bash
export GSETTINGS_SCHEMA_DIR=$HOME/.local/share/glib-2.0/schemas
export QT_QPA_PLATFORM=xcb
```

另有两类**不影响导航**的 rviz2 报错，均已定位：

- **启动时 `GLSL link result : active samplers with a different type refer to the same texture image unit`**：rviz2 自带 OGRE 材质 `indexed_8bit_image` 与新版 Mesa/GLSL 链接器的已知不兼容（[ogre#1252](https://github.com/OGRECave/ogre/issues/1252)、[rviz#463](https://github.com/ros2/rviz/issues/463)）。只在收到第一帧地图时打印一次，地图仍正常渲染，**忽略即可**。
- **关闭 RViz 窗口时 `process has died ... exit code -11`**：`dmesg` 显示段错误固定发生在 `librclcpp.so` 的 `rclcpp::CallbackGroup::~CallbackGroup()`，是 rclcpp Humble 的析构竞态（执行器仍在等待回调组时该组被销毁），只在**退出阶段**触发；运行期间不会崩。可以正常使用，退出时的这条红色报错无实际影响。

> **不要去掉 `MESA_GL_VERSION_OVERRIDE=2.1`**：`display.launch.py` 里给 rviz2 显式加了这个环境变量，让 OGRE 退回旧版 RenderSystem_GL。GL3+ core profile 移除了 1D 纹理，`indexed_8bit_image` 的 `sampler1D` 会直接导致 rviz 崩溃；强制 2.1 后日志仍是 `OpenGl version: 2.1 (GLSL 1.2)`，渲染慢一些但稳定。

### 6.5 机器人到目标点后摆不正 / 原地转不动

先确认不是定位发散（见 6.6），再检查：

- 目标检查器容差：`general_goal_checker` 的 `yaw_goal_tolerance`（当前 0.25 rad）；
- 局部控制器是否允许原地旋转：MPPI 的 `wz_max`（当前 1.9）、`PreferForwardCritic` / `GoalAngleCritic` 权重；
- 机器人是否被卡在恢复循环里（日志反复出现 `Collision Ahead - Exiting Spin`），那通常是 3D 定位跑偏导致代价地图把可行区域当成了障碍（见 6.6）。

### 6.6 3D 重定位失败 / 导航时「飘」（map→odom 跳变或点云对不上）

先区分三种情况：

| 现象 | 含义 | 处理 |
|------|------|------|
| 启动几秒后仍无 `全局重定位成功` | 全局搜索没找到足够好的解（内点率 < `min_inlier_ratio`） | 看下方 ① |
| `全局重定位存在歧义` 告警 | 存在得分接近的对称解（正方形围墙的 90°/180°） | 看下方 ② |
| 运行中反复 `3D 跟踪失败（内点率过低 / 位姿跳变过大）` | ICP 局部跟丢，连续 5 次会自动重新全局搜索 | 看下方 ③ |

**① 全局搜索失败**：

```bash
ros2 param get /fastlio_relocalization prior_map_path   # 路径是否存在
ls -lh src/sam_bot_description/map/prior_3d_map.pcd
ros2 topic hz /cloud_registered                          # 有没有点云
ros2 topic hz /Odometry                                  # FAST-LIO 是否正常
```

- 点云为空 → 先按 §3.2/6.12 确认 Gazebo + FAST-LIO 正常；
- 地图与场地不匹配（改过 world 但没重建 PCD）→ 按 §3.4 重新生成；
- 机器人被搬得太远、或先验地图只有局部 → 调大 `global_search_margin` 的可用范围，或重画更大的地图。

**② 对称解歧义**：先验点云里如果只有四面正方形围墙，90° 旋转后的位姿在几何上无法区分。
本项目用 `global_search_height: 0.35`（只取墙顶/箱顶/球顶这一层做全局搜索）来消除大部分
歧义——地面和墙脚在 (x, y, yaw) 上平移不变，会把对称解“喂”到接近满分。如果仍报歧义：

```bash
ros2 topic hz /aligned_scan    # RViz 里叠加 /prior_map 和 /aligned_scan 看是否重合
```

点云明显错位时，先确认地图是在**同一次场地配置**下生成的；仍不行就按 §3.4 重新建图
（建图时多绕两圈、覆盖箱体和球体周围，能显著增强唯一性）。

**③ 跟踪跟丢**：

- 先按 5.1 节量化误差，确认不是 `gz model` 与 IMU 偏移没换算造成的“假飘”；
- 检查 `map→odom` 是否在做米级跳变：`ros2 run tf2_ros tf2_echo map odom`；
- 点云过稀（< 400 点/帧）时 ICP 容易跟丢，按 6.12 确认 `downsample` 没被改大；
- 临时恢复：`ros2 service call /relocalize std_srvs/srv/Trigger "{}"`；
- 参数上可轻调：`correction_alpha`（1.0 = 完全信任单帧）、`max_tracking_jump`（默认 1.0 m）、
  `icp_corr_dist_tracking`（默认 0.7 m）。改完 `config/relocalization_params.yaml` 重启即可
  （YAML 是符号链接，无需 rebuild）。

> 注意区分两种「飘」：**FAST-LIO 的 odom→base_link 平滑漂移**（转弯航向误差累积，量级
> 约米级/几十米，靠点云密度与 `gyr_cov`）与 **3D 重定位的 map→odom 跳变**（ICP 跟丢，
> 视觉上最明显）。前者是里程计问题，后者是配准问题。

### 6.7 改了 yaml/urdf 不生效

- 改了 `nav2_params.yaml` / `mid360_sim.yaml` / `urdf` / `sdf`：`--symlink-install` 下是软链接，**重新 launch 即可生效**（无需 rebuild）。
- 若当初是用普通 `colcon build`（非 symlink）装的，改了这些文件要重新 `colcon build --symlink-install` 才会复制进 install。

### 6.8 启动时报找不到包 / 找不到 launch 文件

先确认在 `/home/lunyi/myrosproject/CleanRobot_ws` 目录下 `source install/setup.bash`；若仍报错，回到 2.2 重新 `colcon build --symlink-install`。

### 6.9 跑 `run.sh` 时地图还在"边长"、像还在建图

**`run.sh` / `navigation.launch.py` 里没有任何建图节点**（只有 `map_server` 加载静态地图 + `fastlio_relocalization` 做 3D 定位）。出现"边开边长"，是**上一次建图残留的 `slam_toolbox` 进程还在跑**，它在持续往 `/map` 发新地图，并抢发 `map→odom`。

确认方法：

```bash
ros2 topic info -v /map | grep -A1 "Node name"   # 应该是 map_server，出现 slam_toolbox 就是残留
pgrep -af "slam_toolbox|async_slam_toolbox_node"
```

处理：`run.sh` 的清理列表已加上 `slam_toolbox|fastlio_mapping|pointcloud_to_laserscan`，重新跑 `./run.sh` 即可；临时手动清理：

```bash
pkill -9 -f "slam_toolbox|fastlio_mapping|pointcloud_to_laserscan"
```

### 6.10 RViz 里看不到地图（`/map` 没有数据）

按顺序排查：

1. **地图文件本身加载失败**（最常见）。`map/my_map.yaml` 里的 `image:` 必须和同目录下的真实文件名一致。改过图片名（如把 `my_mapnew.pgm` 改名成 `my_map.pgm`）却没改 yaml，就会：
   ```
   [map_server] Failed to open image file
   ```
   此时 `ros2 lifecycle get /map_server` 不是 `active`，`ros2 topic echo /map` 也收不到数据。修法：把 yaml 的 `image:` 改成实际文件名。
2. **话题发布者不对**：`ros2 topic info -v /map` 看 Publisher。导航时必须是 `map_server`（见 6.9）。
3. **整个进程组被挂起了**：`ps -o pid,stat,cmd -p <pid>` 若状态是 `T`，说明被 `Ctrl+Z`（SIGTSTP）或 `kill -STOP` 暂停了，DDS 上一个节点都看不见。恢复：`kill -CONT <pid>`，或重新跑。**退出请用 Ctrl+C，不要按 Ctrl+Z。**
4. RViz 本身崩溃（exit -6/-11）：属本机 OGRE/Mesa 老问题（见 6.4），导航栈不受影响，重开 RViz 即可。

### 6.11 建图时地图几乎不长 / 日志刷 `Message Filter dropping ... queue is full`

```
[slam_toolbox] Message Filter dropping message: frame 'base_link' at time ... for reason
'discarding message because the queue is full'
```

原因：FAST-LIO 发布 `odom→base_link` 比 `/scan` 晚约 0.2 s，slam 的消息过滤器在扫描时间戳上查不到 TF，消息在队列里堆积后被丢弃——**大多数扫描都没进建图**，表现为车开了几米地图只多几格。

`config/mapper_params_online_async.yaml` 已针对本项目把 `transform_timeout` 从 0.2 放大到 **1.0**、`scan_queue_size` 设为 **30**，正常情况下不再丢帧。若仍出现，按顺序检查：

```bash
# 1) TF 是否稳定在 10 Hz 左右（跟不上就会拖慢过滤器）
ros2 topic hz /Odometry
ros2 run tf2_ros tf2_echo odom base_link

# 2) 确认参数已生效（改 yaml 后需要重启 slam_toolbox）
ros2 param get /slam_toolbox transform_timeout
ros2 param get /slam_toolbox scan_queue_size

# 3) 看丢帧是否真的在减少
grep -c "Message Filter dropping" /tmp/build_map_slam.log
```

### 6.12 gzserver 启动几秒后崩溃（`exit code -11`，点云加密导致）

**现象**：把 `mid360.xacro` 的 `<downsample>` 调得比 8 更小（射线更多）后，gzserver 在插件加载完成后约 4 秒崩溃，launch 日志报：

```
[ERROR] [gzserver-1]: process has died [pid ..., exit code -11, ...]
```

`exit code -11` 就是 **SIGSEGV（段错误）**。查内核日志能看到崩溃点：

```bash
dmesg | grep "gzserver.*segfault"
# gzserver[xxxxx]: segfault at 158 ... error 4 in libgazebo_ode.so.11.10.2[...]
```

**根因（已用内核日志 + 反汇编确认）**：崩溃发生在 Gazebo 自带的 ODE 物理库 `libgazebo_ode.so` 内，是一条 **空/野指针解引用**——崩溃指令形如 `movsd 0x158(%rcx),%xmm2`，寄存器 `rcx = 0`（或 `0x158`），即把**非法的旋转/位姿矩阵指针**拿去和向量相乘。它不是我们插件里的数组越界。

**触发条件（实测可复现）**：

| `<downsample>` | 每帧射线数 | 结果 |
|---|---|---|
| 20 | 1000 | 稳定（但点太少，~230 点/帧） |
| 10 | 2000 | 稳定（~450 点/帧） |
| **8** | **2500** | **连续运行 35 min+ 稳定（~590 点/帧）← 当前配置** |
| 5 | 4000 | **两次均崩溃**，`exit -11`，崩点相同 |

**处理**：把 `src/mid360_simulation/urdf/mid360.xacro` 里的 `<downsample>` **改回 8**（或更大），重新 `./run.sh` 即可（xacro 是符号链接安装，无需 rebuild）。`downsample=8` 是当前这套 ODE 多射线实现的安全上限，想再加密需要修复 Gazebo ODE 包装层，成本很高且收益有限（FAST-LIO 另有 `point_filter_num=3` + 0.5 m 体素滤波）。

### 6.13 RViz 里看着没撞、Gazebo 里却撞上障碍物

这是**坐标系没对齐**的典型表现，不是控制器参数问题。本项目踩过下面两类：

1. **代价地图根本没收到激光**。`nav2_params.yaml` 里 obstacle_layer 的 `topic: scan`
   是相对名，Nav2 会把它解析成 `/local_costmap/scan`、`/global_costmap/scan`（0 个
   发布者），障碍层永远是空的——RViz 里看不到障碍，局部避障完全失效。**必须写
   `topic: /scan`**。自检：

   ```bash
   ros2 node info /local_costmap/local_costmap      # Subscribers 里应有 /scan
   ros2 node info /global_costmap/global_costmap    # 同上
   ```

2. **3D 定位的 map 系与 2D 地图相差 0.33 m**。FAST-LIO 的原点是 IMU，PCD 直接保存
   就会让 3D 定位的 `map` 与 `map_server` 的 2D 地图错开一个 IMU 安装偏移；规划器按
   2D 地图避障，实际车体却在偏 0.33 m 的位置。**修复**：`mapping.body_to_base_T`
   （FAST-LIO 发布 `odom→base_link` 时补偿 IMU 偏移）+ `build_3d_map.sh` 保存后用
   `tools/shift_pcd.py` 平移 PCD。自检：

   ```bash
   gz model -m sam_bot -p                      # 真值
   ros2 run tf2_ros tf2_echo map base_link     # 应与其 x/y/yaw 基本一致（静止 < 0.2 m）
   ```

   若两者仍差约 0.33 m，说明 PCD 是旧的（未平移）：`python3
   src/fastlio_localization/tools/shift_pcd.py src/sam_bot_description/map/prior_3d_map.pcd`
   或直接 `./build_3d_map.sh` 重建。

### 6.14 停车后机器人仍缓慢滑动（无 `/cmd_vel` 也在漂）

**现象**：下完目标、`Reached the goal!` 之后，`/cmd_vel` 已经是 0，但机器人在 Gazebo 里
仍以 **约 13 cm/min** 匀速朝当前航向滑动（20 s 移动约 4 cm、几乎不转）。

**原因**：这是 `diff_drive` 插件 + ODE 的物理漂移，**不是定位问题**。两个驱动轮
（`new_link`/`new_link_1`，`mu=1.0`）承担全部地面接触，`cmd_vel=0` 时插件只把目标轮速
设为 0，没有施加「抱死」制动；轮关节 `damping=0.2` 的阻尼不足以完全锁住车体的残余动量，
于是缓慢滑行（两个从动万向轮悬空 2 mm，`mu=0.1`，只偶尔擦碰）。世界本身是平的、重力 −9.8，
所以是差速驱动未制动导致的缓慢蠕变，量级恒定。

**影响与处理**：

- **不影响定位与导航**：FAST-LIO 会实时跟随这个漂移，`map→base_link` 与 `gz model` 真值
  始终一致（连续采样差 ~6 cm）。RViz 里同样能看到车在缓慢移动，不会出现「RViz 没动、
  Gazebo 动了」的错位。
- **需要车停得死**（比如精确对接/停在障碍物旁做演示）时再处理：给两个驱动轮关节加大
  `damping`（如 0.2 → 2.0）或在 `diff_drive` 插件之外加一个「零速即抱死」的摩擦模型。
  改 `sam_bot_description.urdf` 第 5/6 节后需 `colcon build --symlink-install` 重编。
- 测量命令：`gz model -m sam_bot -p` 隔 20 s 取两次，位置差 ×300 即 cm/min 漂移速率。
